# Производительность: как мерить и что движок делает сам

Короткий справочник для авторов игр: чем замерить кадр, что рендер уже батчит и
отсекает без вашего участия и какие привычки в коде игры стоят дорого.

## Чем мерить

### Пример `stress` — нагрузочный стенд

```text
cargo run --example stress                          # все сценарии без окна, таблица в stdout
cargo run --example stress -- meshes sprites_static # только выбранные
STRESS_WINDOW=1 ENGINE_FRAMES=600 cargo run --example stress -- meshes  # в окне, средний FPS в логе
```

Сценарии: `sprites_static` (20 000 неподвижных спрайтов, 4 текстуры вперемешку),
`sprites_moving` (10 000 движущихся), `tilemap` (карта 400×400, камера едет),
`particles` (300 систем), `meshes` (10 000 мешей трёх видов с тенями, большая часть за
кадром), `rigidbodies` (1 500 тел 3D-физики), `hierarchy` (100 цепочек по 30 звеньев,
каждое вращается), `scripts` (20 000 объектов с `on_update`), `ui` (холст на 400 виджетов),
`plain` (20 000 объектов без компонентов — цена «пустой» сцены для подсистем), `churn` (20 000
пустых объектов + каждый кадр создаётся и исчезает по 100 спрайтов со скриптом).

Переменные окружения:

| переменная | по умолчанию | смысл |
|---|---|---|
| `STRESS_RUNS` | 3 | прогонов на сценарий (в таблице — медиана) |
| `STRESS_FRAMES` | 200 | кадров в прогоне (после 30 кадров разгона) |
| `STRESS_STAT` | `p10` | сводка по кадрам прогона: `p10` (10-й перцентиль), `median`, `mean` |
| `STRESS_SCALE` | 1 | множитель числа объектов во всех сценариях |
| `STRESS_WINDOW` | — | `1` — запустить первый выбранный сценарий в окне |

`p10` выбран потому, что на машине с фоновой нагрузкой (сборка, браузер) среднее
«плавает» в разы, а быстрые кадры показывают цену самой работы. Для оценки «что увидит
игрок» берите `STRESS_STAT=mean` на тихой машине.

Колонки таблицы (мс на кадр): `scripts` — хуки компонентов; `physics` — 2D- и
3D-физика; `other` — остальные подсистемы (интерфейс, звук, геймпад); `end` — конец
кадра (уничтожение объектов, события); `render` — рендер на CPU, из него `extract`
(обход сцены, отсечение, сортировка) и `encode` (загрузка буферов, запись команд);
`gpu` — ожидание видеокарты; справа — draw call'ы, спрайты, меши, треугольники и
сколько объектов отсечено.

### Пример `bench` — стенд для сравнения «до / после»

```text
cargo run --example bench                          # витрина, terrain.scene, синтетика: строки BENCH {json}
cargo run --example bench -- showcase_valley       # выбранные случаи (по началу имени)
BENCH_RUNS=1 cargo run --example bench -- --editor-5k   # редактор со сценой на 5 000 объектов
cargo run -p swarm --example bench_swarm           # игры: bench_tashbazar, bench_marble, bench_swarm, bench_lantern
python tools/bench_report.py after.txt before.txt  # таблица и сравнение с шумом
```

Без окна, 1280×720, фиксированные пути камеры; на случай — `BENCH_RUNS` прогонов (3) по
`BENCH_WARMUP` (30) + `BENCH_FRAMES` (150) кадров. В строке: медиана / p95 / p99 кадра, фазы
(скрипты, физика, подсистемы, обход сцены `walk`, извлечение, запись команд, отправка,
ожидание GPU), draw call'ы, треугольники, смены состояния, байты загрузки и аллокации за
кадр, пик кучи, время загрузки. Опыты: `BENCH_SIZE=640x360`, `BENCH_SCALE=0.75`
(`GraphicsSettings::render_scale`), `BENCH_QUALITY=low|medium|high`, `BENCH_NO_SHADOWS=1`,
`BENCH_GFX=shadows,sky,ao,outline,lights,fill,lampshadows,water,flatwater` (включить новые
эффекты), `BENCH_SHOT=<каталог>` (снимок последнего кадра). Отчёт считает изменение меньше
суммы разбросов прогонов шумом. `-- --load-split` (у `bench` и `bench_tashbazar`) — строки
`LOAD {json}`: время до первого кадра по частям — приложение с ассетами, чтение и разбор
сцены, создание объектов, устройство GPU, первый и второй кадр.

Что показал стенд (GTX 1050 Ti): рельеф упирается в пиксели (вторая выборка против повторов
и трипланар скалы — около 70 % его времени; на пресете Low они выключены, рычаг для слабых
GPU — ещё и `render_scale`); предварительный проход глубины рельефа не окупается; 2D-спрайт
стоит ≈ 0.4 мкс в отладочной сборке (обход 43 нс, матрица и углы ≈ 150 нс, квад 60 нс,
склейка с перестановкой текстур ≈ 170 нс); кэш мировых матриц со сравнением TRS при чтении
не окупился и не включён. Загрузка сцены: дольше всего было создание объектов — каждый
экземпляр префаба заново читал и разбирал свой файл; теперь префаб читается один раз на
загрузку (долина витрины 281 → 25 мс, «Ташбазар» 269 → 88 мс; разбор RON — 13 и 5 мс).
Создание устройства GPU с конвейерами — около 0.5–1 с один раз на процесс, первый кадр
долины (рельеф строится целиком) — около 1.4 с.

### Окно и `ENGINE_FRAMES`

Любая игра на `engine::run` понимает `ENGINE_FRAMES=N` (закрыться после N кадров) и
`ENGINE_VSYNC=0/1`. По умолчанию vsync включён (без него движение идёт рывками; для замеров — `ENGINE_VSYNC=0`). В заголовке окна каждые полсекунды —
FPS, draw call'ы и число спрайтов; при закрытии в лог пишется средний FPS:

```text
ENGINE_FRAMES=600 cargo run --example demo3d
[info ] engine_render::window: window closed after 600 frames in 3.1 s: 194 FPS on average
```

### Из кода: `App::profile` и `RenderStats`

```rust
app.tick(1.0 / 60.0);
let profile = app.profile();                      // время последнего tick
println!("scripts {:.2} ms, physics3d {:.2} ms", profile.scripts_ms, profile.subsystem_ms("physics3d"));

let stats: RenderStats = renderer.render(&app.world, &view, width, height);
println!("{} draw calls, {} culled meshes, extract {:.2} ms", stats.draw_calls, stats.culled_meshes, stats.extract_ms);
```

`TickProfile`: `total_ms`, `scripts_ms`, `subsystems: Vec<(&str, f32)>` (по имени
подсистемы: `"physics2d"`, `"physics3d"`, `"ui"`, `"audio"`, …), `end_frame_ms`,
`fixed_steps`. В браузере (`wasm32`) часов нет — все длительности там 0.

`RenderStats` (в оконном режиме лежит в `world.resources` после каждого кадра):
`draw_calls`, `sprites`, `meshes` (нарисованные), `triangles`, `textures`,
`shadow_draw_calls`, `shadow_casters`, `culled_meshes`, `culled_sprites`, `tiles`,
`world_matrices`, `extract_ms`, `encode_ms`.

### Profiler редактора

Окно **Profiler** (Ctrl+7) рисует время кадра по частям — игра (`App::tick`), рендер
сцены, интерфейс редактора, отправка на GPU, ожидание — и счётчики `RenderStats`.
Помните, что редактор сам по себе тратит время на свой интерфейс: итоговую частоту
игры меряйте в окне игры (`engine::run`) или `stress`.

## Что движок делает сам

* **Один проход по сцене.** Рендер обходит активные объекты один раз, неактивное
  поддерево пропускает целиком, мировую матрицу считает один раз на объект и только
  если она нужна (объекты без отрисовки матриц не требуют).
* **Отсечение по камере.** Меши и спрайты, чьи границы целиком вне пирамиды камеры, не
  рисуются (`culled_meshes`, `culled_sprites`). Тайлмап рисует только видимые ячейки.
* **Инстансинг мешей.** Все видимые меши одного вида (`MeshShape` или один и тот же
  ассет) с одной текстурой рисуются **одним** draw call'ом независимо от цвета,
  материала и масштаба: параметры объектов идут вторым вершинным буфером.
* **Тени.** В карту теней попадают только меши, пересекающие объём солнца
  (`Environment::shadow_distance` вокруг камеры), тоже пачками по виду меша.
* **Батчинг спрайтов.** Спрайты, частицы, тайлы и следы с одной текстурой и режимом
  смешивания склеиваются в один draw call. Порядок рисования задают слой сортировки,
  `order` и глубина, при равенстве — порядок иерархии; если подряд идут разные
  текстуры, спрайт переносится в батч своей текстуры, **только если** он ни с кем между
  ними не пересекается на экране, — картинка остаётся той же. Через границу слоя,
  `order` или глубины спрайты не переносятся никогда.
* **Пост-обработка.** При `bloom = 0` цепочка блума не запускается.
* **Физика.** Синхронизация сцены с Rapier смотрит только на объекты с коллайдером
  (или `CharacterController`), находя их по индексу; остальные объекты ничего не стоят.
* **Хуки — только тем, у кого они есть.** Компонент может сказать, какие хуки он
  реализует (`fn hooks(&self) -> Hooks`). Движок держит в сцене списки объектов по
  хукам и в фазе `on_update` проходит только объекты, у которых есть `on_update`:
  20 000 спрайтов и коллайдеров в фазах скриптов не стоят ничего. Все компоненты
  движка-«данные» (`SpriteRenderer`, `MeshRenderer`, `Camera`, `Light`, коллайдеры,
  тела, `AudioSource`, компоненты интерфейса…) объявляют `Hooks::NONE`. Компонент,
  который ничего не объявил, получает все хуки, как раньше. **C++-компоненты** получают
  только те хуки, которые класс переопределил (`engine_component.hpp` отдаёт движку пустые
  указатели на непереопределённые методы; после горячей перезагрузки плагина набор хуков
  обновляется) — 3 000 `Spinner` с одним `on_update` больше не платят за `on_fixed_update`,
  `on_late_update` и прочие пустые вызовы.
* **Варианты шейдера.** Шейдер мешей и рельефа собирается в вариантах: без
  `SoftShadows` — без кода каскадов, без ламп (`ManyLights`, `SpotLight`, `LightShadows`,
  `FillLight`) — без кластеров (docs/api/graphics.md). Выключенный эффект не стоит ни
  регистров, ни выборок.
* **Индекс «тип компонента → объекты».** `scene.find_with::<T>()`, `count_with`,
  `visit_with`, `visit_active_with`, `iter_with`, `for_each_with_mut` стоят
  пропорционально числу объектов с `T`, а не размеру сцены. Интерфейс, звук и физика
  находят свои компоненты через этот индекс: объекты без UI, звука и коллайдеров для них
  бесплатны. Индекс обновляется лениво при добавлении/удалении компонентов; порядок
  иерархии пересчитывается, только когда иерархия меняется (создание объекта в корне и
  ребёнка только что созданного родителя — без пересчёта).
* **Конец кадра** сжимает списки компонентов только у объектов, где что-то удаляли.

## Ориентиры

`stress` на машине разработки (GTX 1050 Ti, отладочная сборка движка, `STRESS_STAT=p10`, медиана
трёх прогонов; машина была загружена, разброс между прогонами до 1.5–2×), мс на кадр:

| сценарий | скрипты | физика | прочие подсистемы | конец кадра | рендер CPU | весь кадр |
|---|---|---|---|---|---|---|
| `plain` (20 000 пустых объектов) | 0.001 | 0.015 | 0.008 | 0.001 | 0.78 | 1.8 |
| `sprites_static` (20 000 спрайтов) | 0.002 | 0.025 | 0.013 | 0.002 | 7.1 | 8.2 |
| `scripts` (20 000 `on_update`) | 2.8 | 0.028 | 0.018 | 0.002 | 1.5 | 4.8 |
| `churn` (±100 объектов за кадр) | 0.64 | 0.026 | 0.012 | 0.29 | 1.6 | 3.9 |
| `particles` (300 систем) | 0.12 | 0.020 | 0.009 | 0.001 | 0.86 | 1.5 |

Объекты без скриптов, коллайдеров, звука и интерфейса почти ничего не стоят ни скриптам, ни
подсистемам; основное время больших 2D-сцен — извлечение спрайтов в рендере (≈0.4 мкс на спрайт).

## Глубина: обратная (reversed-Z)

Сцена рисуется с **обратной глубиной**: ближняя плоскость камеры — глубина 1, дальняя — 0,
буфер `Depth32Float` очищается нулём, тест — «больше». С обычной глубиной (0 у камеры) почти
вся точность `f32` уходит в первые метры: при `near = 0.04` различимый зазор на 100 м — около
1.5 см, на 500 м — 37 см, на 1 км — 1.5 м, и близкие поверхности вдали (стекло в раме, плитка
на мостовой, карниз на стене) «мерцают, как наложение текстур». С обратной глубиной точность
почти одинакова на любом расстоянии и почти не зависит от `near`:

| `near` | различимый зазор, обычная глубина: 100 м / 500 м / 1 км | обратная глубина: 100 м / 500 м / 1 км |
|---|---|---|
| 0.04 | ≈ 1.5 см / 37 см / 1.5 м | ≈ 0.05 мм / 0.25 мм / 0.5 мм |
| 0.1 | ≈ 6 мм / 15 см / 60 см | ≈ 0.05 мм / 0.25 мм / 0.5 мм |

(обратная: около 2⁻²² от расстояния — предел самой арифметики `f32` вершин; на практике
планируйте зазоры от 1 мм.) Проверка — `crates/engine/tests/depth_precision.rs`: плиты с
зазором 5 мм … 5 см на 20 … 800 м при `near` 0.04 и сдвиг камеры на 1 мм.

**Свои матрицы.** Камеры (`Camera`, `CameraView::look_at`, `CameraView::orthographic_2d`)
строят матрицы сами. Если вы собираете `CameraView::view_proj` вручную, берите
`engine_render::perspective(fov_y_рад, aspect, near, far)` и
`engine_render::orthographic(left, right, bottom, top, near, far)` (обе — правая система,
камера смотрит в −Z, обратная глубина). Матрицу с обычной глубиной (`Mat4::perspective_rh` …)
рендерер распознаёт (точка глубины 0.75 дальше от `position`, чем 0.25), переводит сам и
один раз пишет предупреждение в лог — кадр верный, но точность уже потеряна в матрице.
Поэтому `position` вида должна быть точкой камеры. Восстанавливая точку по глубине
(`inv_view_proj`), помните: z = 1 — ближняя плоскость, z = 0 — дальняя
(`engine_render::depth::{NEAR_DEPTH, FAR_DEPTH}`). Карта теней солнца — отдельная цель с
обычной глубиной (ортографическая проекция, точность равномерна).

## Советы

1. **Мало текстур — мало draw call'ов.** Собирайте спрайты в листы
   (`SpriteRenderer::sheet`), тайлы — в один тайлсет. Каждая отдельная текстура — это
   минимум один draw call на «кучку» спрайтов.
2. **Меши — одного вида.** Тысяча `MeshRenderer::cube()` разных цветов — один draw call;
   тысяча разных `.obj` — тысяча. Повторяйте ассеты, различайте их цветом и масштабом.
3. **Слои и `order` разбивают батчи.** Спрайты в разных слоях или с разным `order` не
   склеиваются между собой, даже с одной текстурой. Не давайте каждому спрайту
   уникальный `order` без нужды — сортируйте слоями.
4. **Пересекающиеся спрайты разных текстур** рисуются строго по порядку и не
   склеиваются. Густая толпа из спрайтов четырёх текстур — до четырёх draw call'ов на
   каждое «перекрытие»; лист спрайтов снимает проблему целиком.
5. **Тени.** `without_shadows()` для земли, мелочи и всего, что тень не отбрасывает
   заметно; держите `Environment::shadow_distance` таким, какой нужен игре.
6. **Выключайте, а не прячьте.** `scene.set_active(id, false)` убирает поддерево из
   обхода рендера, физики и `on_update`. Объект за кадром, но активный, по-прежнему
   получает `on_update` каждый кадр.
7. **`on_update` — не для всех.** 20 000 объектов с пустым по смыслу `on_update` стоят
   миллисекунды. Компоненты-данные пусть объявляют `fn hooks(&self) -> Hooks { Hooks::NONE }`
   (скрипты — только свои хуки): тогда их нет в фазах кадра вовсе. Один «менеджер», который обходит своих подопечных, дешевле тысяч
   скриптов. Тяжёлую логику — в `on_fixed_update` или по таймеру (`ctx.after`).
8. **Не ищите объекты по имени каждый кадр.** `find_by_name` и `find_by_tag` обходят всю
   сцену; найдите один раз в `on_start` и храните `GameObjectId`. Запросы по типу
   (`find_with`, `visit_active_with`, `count_with`) идут по индексу и дёшевы.
9. **Глубокие иерархии** сами по себе дёшевы для рендера, но `scene.world_matrix(id)`
   и `world_position` в скриптах поднимаются по родителям при каждом вызове — не зовите
   их в циклах по тысячам объектов.
10. **Частицы.** Стоимость — число живых частиц (CPU-симуляция и квады). Ограничивайте
    `max_particles` и `emission_rate`, у дальних эффектов уменьшайте их.
11. **Сборка.** Отладочная сборка движка оптимизирована не полностью (свой код —
    `opt-level = 1`); итоговые цифры проверяйте `cargo run --release`.
