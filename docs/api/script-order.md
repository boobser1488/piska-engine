# Порядок выполнения скриптов и сортировка в редакторе

Два связанных средства: **Script Execution Order** (Unity: Edit → Project Settings → Script
Execution Order) — в какой последовательности компоненты получают `on_start`, `on_update` и
остальные хуки, и **сортировка, фильтры и группировка** скриптов и ассетов в окнах редактора.

## 1. Порядок выполнения

У каждого типа компонента есть целое число (по умолчанию 0). Меньше — раньше. Оно действует на
`on_start`, `on_fixed_update`, `on_update` и `on_late_update`: сначала **все** компоненты с порядком
−100 (на всех объектах сцены), потом все с 0, потом все с +100. Внутри одного числа остаётся прежний
порядок: иерархия (родитель раньше детей, братья — как в окне Hierarchy), затем порядок компонентов
на объекте.

```rust
use engine::prelude::*;

component! {
    /// Читает ввод и кладёт его в ресурс: должен отработать раньше всех, кто его использует.
    pub struct InputReader { pub deadzone: f32 = 0.2 }
}
impl Component for InputReader {
    fn execution_order(&self) -> i32 { -100 }          // раньше обычных скриптов
    fn on_update(&mut self, ctx: &mut Ctx, _dt: f32) { /* … */ }
}

component! { pub struct CameraFollow {} }
impl Component for CameraFollow {
    fn execution_order(&self) -> i32 { 100 }           // после всех, кто двигает цель
    fn on_late_update(&mut self, ctx: &mut Ctx, _dt: f32) { /* … */ }
}
```

`on_destroy` и `on_message` порядка выполнения **не учитывают**: они идут для объекта целиком, как раньше
(иерархия, затем порядок компонентов). Порядок компонентов на объекте можно менять в инспекторе —
перетаскиванием заголовка или «⋮» → Move Up / Move Down (действие `Action::MoveComponent`) — это
решает порядок при равных числах.

## 2. Откуда берётся число

От слабого источника к сильному:

1. **Код.** `Component::execution_order(&self) -> i32` (по умолчанию 0). Спрашивается один раз, при
   добавлении компонента на объект. Узнать значение без объекта можно через
   `TypeRegistry::default_order_of("Имя")`.
2. **Настройки проекта.** Файл `project.settings` в корне каталога ассетов перекрывает код по
   **имени типа**:

   ```ron
   (
       script_order: {
           "InputReader": -100,
           "CameraFollow": 100,
       },
   )
   ```

   Тип, которого нет в файле, берёт число из кода. Отсутствующий файл — всё из кода.

`engine::mount_assets` читает `project.settings` и применяет настройки к миру, а `piska-export` кладёт
файл в пак ассетов вместе с остальными, поэтому экспортированная игра работает в том же порядке. Битый
файл не мешает запуску: в лог идёт предупреждение с именем файла, порядок — из кода.

Из кода настройки применяются так (в тестах, в своих редакторах):

```rust
let mut settings = ProjectSettings::default();
settings.set_order("InputReader", -100);
app.world.apply_project_settings(settings);   // действует на созданные и будущие компоненты
// чтение / запись файла:
let settings = ProjectSettings::load("assets/project.settings")?;   // нет файла — по умолчанию
settings.save("assets/project.settings")?;
```

Смена порядка во время работы пересортирует списки вызова **один раз**, а не каждый кадр. Настройки
переживают смену сцены (`load_scene`, Stop в редакторе).

Имя типа — то же, что в файле сцены (`stringify!` имени структуры; у C++-компонентов — имя класса).
Поэтому порядок C++-компонента задаётся настройкой проекта; объявить число прямо в коде C++ пока
нельзя (см. §7).

## 3. Project Settings в редакторе

**Edit → Project Settings… → Script Execution Order** (страница окна настроек проекта, см.
`editor.md`, «Окна настроек»; из кода — `editor.show_project_settings_page("script-order")`):

* список типов с числами в порядке выполнения; линия **Default Time** на нуле показывает, где стоят
  все, кого в списке нет;
* **Add script** — поиск по всем зарегистрированным компонентам (Rust, C++, Scenario и движка) с
  меткой языка; новый тип получает число из своего кода;
* строку можно **перетащить** за точки слева: число подбирается между соседями (середина), на краях
  — ±100; если между соседями нет целого числа или они равны, числа этой стороны от линии
  пересчитываются с шагом 10. Строка не перескакивает линию Default Time;
* число каждой строки правится в поле (перетаскивание мышью или двойной щелчок и ввод), «✕» убирает
  тип из списка — он вернётся к порядку из кода;
* **Apply** пишет `project.settings` и применяет порядок сразу, в том числе в режиме Play. **Revert**
  возвращает список к записанному. Пока есть несохранённые правки, рядом написано «Unsaved changes».
  Остальные страницы Project Settings пишут файл сразу; неприменённый порядок они не трогают —
  в файл попадает действующий. **Reset page** / **Reset all** очищают список (с подтверждением)
  и записывают файл сразу.

Типы, которых нет в этом редакторе (плагин C++ не загружен), остаются в списке с пометкой *Not
registered*: порядок применится в игре, которая их регистрирует.

Управление из кода и тестов: `editor.show_project_settings(true)`, `set_script_order(name, n)`,
`remove_script_order(name)`, `script_order_draft()`, `script_order_is_dirty()`,
`apply_script_order()`, `revert_script_order()`; идентификаторы для щелчков —
`Editor::script_order_row_id(name)`, `script_order_handle_id(name)`, `script_order_apply_id()`,
`script_order_revert_id()`, прямоугольник строки — `script_order_row_rect(name)`.

## 4. Что именно гарантируется

* В каждой фазе (`on_start`, `on_fixed_update`, `on_update`, `on_late_update`) компоненты вызываются
  по возрастанию порядка; при равных числах — иерархия, затем порядок на объекте.
* Если ни у одного компонента сцены нет числа, отличного от 0, диспетчер работает точно как до
  появления порядка (по списку объектов).
* **Компонент, добавленный в хуке, в сцене с порядком выполнения вызывается со следующего кадра**
  (список вызова — снимок на начало фазы), а не в этой же фазе. Без порядка выполнения компонент,
  добавленный на *этот же* объект, по-прежнему вызывается в этой же фазе. Удалённый компонент в этой
  фазе уже не вызывается.
* `on_start`: компоненты, которые добавили в `on_start` объектам, созданным до начала фазы,
  стартуют в этой же фазе — следующим «кругом» (не более 8 кругов).
* Неактивные объекты пропускаются в момент вызова, как раньше.

## 5. Стоимость

Диспетчер по-прежнему идёт только по компонентам, у которых есть хук (`hooks()`): тысячи «данных»
ничего не стоят. В сцене с порядком выполнения список вызова строится один раз и кэшируется — он
пересобирается, только если менялись иерархия, состав компонентов или настройки. Пока ни у кого нет
числа ≠ 0, дополнительной работы нет вовсе. Проверки: `crates/engine-core/tests/exec_order.rs`
(число вызовов не растёт; кадр с порядком не дороже обычного более чем в разы).

## 6. Сортировка, фильтры, группы в редакторе

**Project.**

* **Sort** (справа на полосе под путём): Name, Type, Date modified, Size; по возрастанию и убыванию.
  Каталоги всегда впереди. Имена сравниваются по-человечески: без регистра, числа по значению
  (`Level2` раньше `Level10`).
* **Чипы типов**: All, Scripts (Rust, C++ и `.scenario`), Scenes, Prefabs, Models, Materials,
  Textures, Audio, Other. Можно включить несколько сразу. Работают в плитках, списке и результатах
  поиска; каталоги остаются, чтобы можно было ходить дальше.
* **Список** показывает столбцы Name, Type, Modified, Size; щелчок по заголовку сортирует (стрелка —
  направление; первый щелчок по Modified и Size — «сначала новые / большие»). В узком окне Modified и
  Type скрываются.
* **Code** показывает исходники по языкам — Rust, C++, Scenario, — у каждой группы заголовок со
  счётчиком.
* Выбор запоминается в настройках редактора (`editor.ron`): `project_sort`, `project_sort_desc`,
  `project_types`.

**Add Component** (инспектор): компоненты по сворачиваемым категориям — Rendering, Physics 2D,
Physics 3D, Audio, UI, Effects, затем Scripts (Rust), Scripts (C++), Scripts (Scenario); внутри — по
алфавиту. Сверху — **Recent** (последние добавленные). Поиск идёт по всем категориям, лучшие
совпадения первыми: точное имя, начало имени, начало слова (`ren` → *Sprite Renderer*), подстрока.

Категория берётся из реестра типов:

```rust
registry.register_in::<MyBeacon>("Gameplay");          // свой раздел меню
registry.categorize(&["Door", "Lever"], "Gameplay");   // уже зарегистрированным
registry.category_of("Door");                          // Some("Gameplay")
```

Тип без категории — скрипт игры («Scripts»); C++ получает «Scripts (C++)», `ScenarioRunner` —
«Scripts (Scenario)», типы движка (рендер, физика, звук, интерфейс) назначены в их
`register_components`. **Свой компонент движка из нового крейта нужно отнести к категории
в `register_components`**, иначе он окажется среди скриптов.

**Инспектор**: компонент перетаскивается за заголовок на другой компонент, в меню «⋮» есть Move Up /
Move Down. **Hierarchy**: в меню объекта **Sort Children A-Z** один раз сортирует детей по имени
(отменяется Ctrl+Z).

Управление из кода и тестов: `editor.project_sort()` / `set_project_sort("size", true)`,
`project_type_filters()` / `set_project_type_filters(&["scripts"])`, `set_project_search(text)`,
`set_project_list_view(true)`, `project_shown()` (имена в нарисованном порядке),
`project_group_headings()`; идентификаторы — `Editor::project_filter_chip_id("scripts")` (или
`"all"`), `Editor::project_sort_header_id("size")`; действия `Action::MoveComponent { object, from, to }`
и `Action::SortChildren { parent }`.

## 7. Чего нет

* **C++:** число нельзя объявить в самом классе (нужно было бы менять ABI и `engine_component.hpp`);
  порядок C++-компонента задаётся в Project Settings по имени класса и работает так же, как для Rust.
* Порядок не влияет на `on_destroy` и `on_message`, а также на `on_collision_enter` /
  `on_trigger_enter` (они доставляются по объектам).
* Перетаскивание строк в Project Settings выбирает числа по соседям; тонкий порядок внутри группы
  с одинаковыми числами задаёт инспектор (порядок компонентов на объекте) и иерархия.
